# Global hotkey manual checklist

The desktop hotkey (default Ctrl+Shift+F, Cmd+Shift+F on macOS) is the second trigger next to the extension command. The app listens through the first backend that starts, in this order: evdev (Linux, needs keyboard access), the SharpHook hook (Windows, macOS, and X11 sessions), then the desktop's own shortcut (GNOME, KDE, Hyprland, Sway) pointed at `juvin --trigger`. The Shortcuts section and wizard step 4 show which one is listening.

## Steps (any OS)

1. Start the app with `XDG_DATA_HOME` (Linux) or the equivalent pointing at a scratch directory, with the extension connected in a browser that has the bundled test page or a Gmail draft open.
2. Open Settings, Shortcuts. The status line must name the backend ("Listening through Keyboard devices", "the keyboard hook", or the desktop) and the Test row must show Detected for two seconds after a press.
3. Focus the browser, select the draft, press the shortcut. The panel must open at the top right and stream a rewrite; the log must show one `Captured ... adapter ...` line and, where the browser command fires too (Windows, X11, and evdev on Wayland), one `Coalesced duplicate press.` line. On the desktop-shortcut route the compositor consumes the key before the browser sees it, so there is no duplicate to coalesce.
4. Focus another app and press the shortcut. The panel must show "Focus the browser with your draft and press the shortcut again." and the log `Capture declined (browser-not-focused)`.
5. Close the browser and press the shortcut. The panel must say no browser is connected (`no-browser`), and Recapture must be disabled.
6. Record a new shortcut in the Shortcuts section (click the chord, press the keys). Pressing the current shortcut while recording must not open the panel. The new chord must be listed, and the backend must restart with it.
7. Run `juvin --trigger` from a shell while the browser is focused. It must exit 0 and start a capture when the desktop shortcut is the active backend or nothing listens; otherwise the log says `Trigger ignored while <backend> listens.`
8. Grep the log for three words from the draft: no matches. Logs carry only lengths, counts, ids, and codes.

## Linux extras

- Wayland without keyboard access: the wizard checklist shows "Keyboard access" as Recommended with "Allow keyboard access". The action installs `/etc/udev/rules.d/70-juvin-input.rules` through pkexec and the hotkey service restarts on evdev without a sign-out. Declining leaves the desktop shortcut route.
- Desktop shortcut route (pick it in the Shortcuts section or run without keyboard access): GNOME writes a custom keybinding that applies live; KDE writes `~/.local/share/kglobalaccel/juvin-rewrite.desktop` and the section says it applies after the next sign-in; Hyprland writes `~/.config/hypr/juvin.conf`, sourced once from `hyprland.conf`, and reloads; Sway writes a marked block in `~/.config/sway/config` and reloads. "Remove desktop shortcut" takes it out and the status drops to not listening. A failed `hyprctl` or `swaymsg` reload is reported with the command to run and retried on the next start.
- Hyprland panel: after the panel shows, `hyprctl -j clients` must list the `juvin` window titled "Juvin rewrite" with `pinned: true`, and switching workspaces must keep it visible (checked October 12, 2026 on VM 840: pinned after the first show, followed workspace 2, still pinned after hide and show).
- Sway panel: after every show, `swaymsg -t get_tree` must list the `juvin` window titled "Juvin rewrite" as a sticky floating container 16 px from the top right of its workspace, below the bar, and switching workspaces must keep it visible.
- Switching to another backend removes an idle desktop shortcut. On KDE the live binding stays until the next sign-in, which is why `juvin --trigger` is ignored while another backend listens.

## Notes for automation

- Fedora: `ydotool key 29:1 42:1 33:1 33:0 42:0 29:0` is a real Ctrl+Shift+F for evdev and for a browser under XWayland. XTEST (`xdotool key`) reaches the browser but not evdev. Avalonia windows run under XWayland too; focus the client window, not the `mutter-x11-frames` decoration, before sending keys or they go nowhere.
- Marionette sets `focusmanager.testmode`, which makes Firefox report focus while minimized; set it to false before testing `browser-not-focused`.
- Windows: the app, Chrome, SendKeys, and `juvin --trigger` must all run in the interactive session (the control pipe name carries the session id); a one-shot scheduled task with `/it` running a request loop works. `LOCALAPPDATA` alone does not redirect the app's data folder; the run temporarily pointed the HKCU "Local AppData" shell folder at the scratch directory and restored it. Chrome ignored `--load-extension`; CDP `Extensions.loadUnpacked` loaded the pinned id.
- VM 840 on KDE: ydotool's absolute pointer moves do not land; click Avalonia windows with `xdotool` (XTEST) after approving KWin's "Control input devices" prompt once, and send keys with ydotool so evdev sees them. A layout set with `kwriteconfig6 --file kxkbrc` takes effect at the next sign-in.
- VM 840: Hyprland does not export its `WAYLAND_DISPLAY` and `DISPLAY` in its own environ; read a child's. pkexec needs a polkit agent in the graphical session scope; `polkit-kde-authentication-agent-1` started from inside the session works, one started over SSH does not. When the app runs with a scratch `XDG_DATA_HOME`, the KDE writer follows it, so give the app the session's data directory for a KDE delivery check. `grim` and `spectacle` were installed for screenshots.
- The Codex-driven runs and their scripts were under `/tmp/juvin-hotkey-verify`, `/tmp/juvin-win-hotkey`, and `/tmp/juvin-840` (temporary).
